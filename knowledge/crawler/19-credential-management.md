# S2 凭证管理（D6 · 产品侧）

> 衔接 B4 第 5 课（凭证生命周期 + S3 四件套设计蓝图）→ 本单元把蓝图**产品化**：PageHarvest factory-monitor 凭证处理从"被动标记"升级为"状态机 + 主动探活"。
> 本手册 = 设计蓝图（学习产物）；产品实现走 Reasonix（P3 阶段，排期后动）。

## 0. 场景（活教材）

factory-monitor 现状（2026-08-19 核对）：
- `fetcher.py`：403 → 换 UA 重试 1 次 → 失败标记 `COOKIE_EXPIRED`（**被动检测**：业务请求撞墙才发现）
- `~/.pageharvest-data/factory-monitor/COOKIE_EXPIRED` 标记文件 → 通知人工重登
- 1688 cookie 08-10 过期案例：过期后整批请求 403 → 人工重登 → 撞滑块（内容层）→ 手动画

B4-15 卡片（T15，08-19 满分）：主动探活赢在**时间差**——死即知（业务请求未发、损失为零）；被动=整批 403 + 重登撞验证码连锁。

## 1. 一句话本质

**凭证不是"有/无"，是状态机**；采集系统的目标不是"永远不死"，而是"死了立刻知道、按状态转移、别让整批请求撞墙"。

## 2. 凭证状态机（第 1 课核心）

```
┌─────────┐   探活正常    ┌─────────┐
│  有效    │───────────▶│  濒死?   │
│ ACTIVE  │◀───────────│ SUSPECT │
└────┬────┘   连续N次    └────┬────┘
     │ 探活判死               │ 探活判死
     ▼                       ▼
┌─────────┐   自动重登成功   ┌─────────┐
│  失效    │──────────────▶│ 重登中   │
│ DEAD    │                │ RENEWING│
└────┬────┘                └────┬────┘
     │ 刷新失败/放弃             │ 失败
     ▼                          ▼
┌─────────┐                人工介入/放弃
│  放弃    │◀────────────────────────
│ ABANDON │
└─────────┘
```

| 状态 | 进入条件 | 可执行动作 | 退出条件 |
|------|---------|-----------|---------|
| ACTIVE 有效 | 凭证通过校验 | 正常采集（全速） | 探活判死/到有效期 |
| SUSPECT 濒死 | 首次探活异常/临近过期 | 降频采集（半速）、加密探活 | 连续 N 次探活正常 → 回 ACTIVE；再异常 → DEAD |
| DEAD 失效 | 探活确认死亡 | 触发刷新（分级）、降级=暂停采集 | 刷新成功 → RENEWING→ACTIVE；失败 → ABANDON |
| RENEWING 重登中 | 刷新流程启动 | 自动重登（有账号密码）/半自动（扫码/打码）/人工 | 新凭证通过校验 → ACTIVE；失败超时 → ABANDON |
| ABANDON 放弃 | 刷新失败/人工决定 | 通知 + 该凭证退出轮换池 | 人工更换新凭证 → ACTIVE |

**为什么状态机而不是布尔**：
- 布尔只有"活/死"，丢失**中间态**——濒死（SUSPECT）是最值钱的信号：还没死就降频，避免"突然死"的整批损失
- 每个状态绑定**该做什么**（动作），而不是"死了再说"——把 B4 的四件套（检测/刷新/轮换/降级）落成状态转移动作

## 3. 四件套 → 状态机映射

| 四件套 | 状态机中的落点 |
|--------|---------------|
| 检测 | 探活定时器（驱动状态转移的观察器）：定时发轻量请求 → 判死/判活 |
| 刷新 | DEAD→RENEWING→ACTIVE 路径：自动重登优先 → 半自动兜底 → 人工介入 |
| 轮换 | 多凭证池：单凭证 DEAD → 切池中下一个 ACTIVE 凭证，采集不中断 |
| 降级 | SUSPECT 降频 / DEAD 暂停采集（别让整批请求撞墙 = 时间差收益的兑现） |

## 4. 主动探活设计三要素（衔接 T15）

1. **发什么**：轻量请求——需登录态的轻接口/页面（如 1688 的某个低价接口或用户中心页），**单请求低频**，不带业务负载；严禁用"业务请求本身"当探活（那是被动）
2. **多久发**：低频定时（如每 10-30 分钟一次），比业务采集频率低一个量级——探活本身不能成为风控信号（B4-10/T15：悄悄试探不惊动风控）
3. **怎么判断**：响应特征而非状态码——跳登录页（302 到 login）/ 未登录 JSON（特定字段）/ 验证码页 / 正常页。**连续 N 次异常才判 DEAD**（单次抖动不判死），连续 N 次正常才回 ACTIVE（防抖双边）

## 5. 项目落点（现状 → 目标）

| 环节 | 现状（被动） | 目标（主动） |
|------|------------|------------|
| 检测 | 403 重试 1 次 → COOKIE_EXPIRED 标记 | 探活定时器（轻量请求 + 响应特征判断） |
| 刷新 | 人工重登（通知→手动） | 分级：自动重登（存账号密码时）→ 半自动 → 人工 |
| 轮换 | 单凭证 | cookie 池（cookies.json 已有多域凭证，池化改造） |
| 降级 | 无（整批 403 才停） | SUSPECT 降频 / DEAD 暂停 + 通知 |

- 对应飞轮提案 1（S3 主动探活）——学习课出设计，代码实现走 Reasonix（P3 排期）
- 验收口径：cookie 过期 → 探活先于业务请求发现 → 降级暂停 → 自动/人工刷新 → 恢复，**全程业务请求零 403 撞墙**

## 6. 钩子池（深入 · 第 4 课 08-29 已答）

### H1：探活请求本身被风控盯上怎么办？

**核心矛盾**：探活要够勤才能及时发现 cookie 死亡，又不能太勤变成风控信号。

**三层破解（递进：模糊信号 → 消除信号 → 稀释信号）**：
1. **降频 + 抖动（治标）**：间隔加随机抖动（如 10min ± 3min），破坏机械节拍——风控异常检测多靠周期性；但只是让信号变模糊，没消除
2. **换通道（治本）**：探活走轻接口/独立端点（用户中心页/价格接口），与业务采集请求特征分道扬镳；登录态检查类请求风控阈值比业务请求宽松
3. **多凭证分摊（釜底抽薪）**：探活压力分摊到多个凭证，单凭证信号强度自然低于阈值——同时是 H2 轮换池的收益

**记忆点**：探活被盯 = 信号强度问题 → 降频抖动（模糊）/ 换通道（消除）/ 多凭证分摊（稀释）

**类比（画像库：公司工牌 + 机场安检）**：探活被盯 = 员工每天固定时间刷工牌进公司，保安盯上你“怎么天天同一分钟打卡”——降频抖动 = 打卡时间随机化（还是每天刷）；换通道 = 改走侧门（换一个不常查的入口）；多凭证分摊 = 多个员工轮流刷（每个员工看起来都很正常）。轮换策略 = 工牌池：优先用最久没刷的那张（LRU 雨露均沾，避免某张长期闲置被挂失），死卡直接跳过（健康度筛选）。

### H2：cookie 池轮换策略——下一个凭证选谁？

**实际工程答案：LRU 均衡 + 健康度筛选（不是纯健康度排序）**：
- **LRU 管“用谁”**：正常时按最近最少使用轮换，雨露均沾——治闲置风险（长期不用的凭证行为异常，闲置即风险）
- **健康度管“排除谁”**：SUSPECT/DEAD 直接跳过——筛选器不是排序器
- 纯健康度排序的缺点：需维护健康度数据、实现重

**记忆点**：轮换策略 = LRU 均衡 + 健康度筛选；“闲置即风险”是隐蔽工程易漏洞察

- Q: 凭证状态机 5 个状态分别是什么？为什么不能用"活/死"布尔值代替？
  A: - 5 态：ACTIVE 有效 → SUSPECT 濒死 → DEAD 失效 → RENEWING 重登中 → ABANDON 放弃；ACTIVE↔SUSPECT 由连续 N 次探活结果驱动
  - 布尔只有"活/死"，丢**中间态 SUSPECT**——它最值钱：濒死就降频半速（提前止损），避免"突然死"的整批损失；每个状态绑定"该做什么"（动作），而不是"死了再说"

- Q: 主动探活三要素？为什么探活请求必须"轻"且"低频"？
  A: - 三要素：发什么（轻量请求：需登录态的轻接口，绝不用业务请求当探活）/ 多久发（低频定时，比采集频率低一个量级）/ 怎么判（响应特征：跳登录页/未登录 JSON/验证码页；连续 N 次异常才判死、N 次正常才回 ACTIVE——双边防抖）
  - 必须轻+低频：探活本身不能成为风控信号——量≈业务量 = 给自己加一个"定时打卡"信号，等着被封

- Q: 场景题：探活发现 cookie 死了，采集任务正在跑——接下来按什么顺序处理？降级怎么设计才能避免整批请求撞墙？
  A: - 完整链路：① **暂停采集**（DEAD 止损，你答了）→ ② **有轮换池先切备用凭证**（无缝切换，采集不中断；没池子才走重登）→ ③ **刷新分级**：自动重登（有账号密码）→ 半自动（扫码/打码）→ 人工介入（factory-monitor 现状）→ ④ **恢复条件**：新凭证通过校验 + **连续 N 次探活正常才回全速**（刚重登就全速 = 重登+高频双风控信号）→ ⑤ 失败超时 → ABANDON 通知人工
  - 降级两档：**SUSPECT 降频半速（提前）+ DEAD 暂停（止损）**——不是一锤子

- Q: 四件套在状态机里各是什么角色？轮换 vs 刷新的关系？缺轮换/缺降级分别什么后果？
  A: - 角色：检测=观察者（只报告不救火：判死/判活、触发状态转移；不亲自执行刷新/轮换/降级）；刷新/轮换/降级=执行者
  - 轮换 vs 刷新：轮换=换池中下一个 ACTIVE 凭证（无缝，采集不中断）；刷新=重新登录换新凭证（死马当活马医）。**轮换优先，池子空了才刷新**
  - 缺轮换：单凭证死→无备用可切→采集停摆（人工介入期间全停）
  - 缺降级：无 SUSPECT 降频半速→濒死期仍全速→业务请求撞墙才发现→整批 403 + 重登撞滑块连锁（1688 案例）
  - ⚠️ 降级=止损（不是隐蔽）；隐蔽性是探活的设计目标（悄悄试探不惊风控）

- Q: ① 探活与业务采集为什么要解耦？耦合的后果是什么？② DEAD 状态为什么需要“暂停采集”这个闸？③ 刷新成功后的恢复条件是什么？
  A: - 解耦：探活=观察者（独立定时器只判生死），业务=执行者（只消费状态）——耦合=用业务请求当探活，探活失败=业务失败，且探活会干扰业务节奏
  - DEAD 暂停闸：DEAD 后继续请求 = 整批撞墙（403+滑块连锁）；暂停 = 止损 + 给刷新留时间窗
  - 恢复条件：新凭证通过校验 + **连续 N 次探活正常才回全速**（刚重登就全速 = 重登+高频双风控信号）

- Q: ① 探活被风控盯上，三层破解是什么？为什么“降频抖动”只是治标？② 轮换策略为什么用“LRU + 健康度筛选”而不是纯健康度排序？闲置凭证有什么风险？③ 给 factory-monitor 设计探活：选哪条通道（1688 场景）？间隔多少？怎么防被盯？
  A: - H1 三层（递进：模糊→消除→稀释）：降频+抖动（模糊信号，没消除）/ 换通道（消除信号，轻接口与业务特征分道） / 多凭证分摊（稀释信号）
  - H2：LRU 管“用谁”（均衡、治闲置风险） + 健康度管“排除谁”（筛选器非排序器）；闲置凭证长期不用 = 行为异常
  - H3：探活间隔必须 < 业务采集间隔（才能提前发现）；factory-monitor 业务 09:30/21:30 间隔 ~12h → 4h 折中合理；防被盯选换通道（用户主页轻接口）
