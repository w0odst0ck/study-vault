# 多厂商采集策略评估

> 来源：智能照明方案馆第二轮采集（2026-07-25）
> 关键词：厂商评估框架 · 详情页发现 · 动态降级 · parallel 批量采集

## 厂商采集评估框架

### 四维评估

| 维度 | 考量指标 | 决策 |
|------|---------|------|
| **页面结构** | 静态 HTML / 动态 JS / SPA | 静态 √ → 直接采集；动态 → 试 playwright，失败降级 |
| **详情页可发现性** | 独立 URL / 分组目录 / 仅列表 | 独立 URL → 全量抓取；仅目录 → 降级 catalog |
| **反爬强度** | robots.txt / 频率限制 / 验证码 | 轻量 → 动态延迟；重度 → manual |
| **内容质量** | 方案详情 / 产品参数 / 品牌介绍 | 有详情 → 采集；仅品牌介绍 → catalog |

### 决策树

```
页面是否静态 HTML？
├── 是 → 是否有独立详情页 URL？
│   ├── 是 → 全量采集（kingsun/fsl/ltech）
│   └── 否 → 降级 catalog（雷士照明）
└── 否（动态 JS）→ 尝试 playwright
    ├── 成功 → 全量采集
    └── 失败 → 降级 catalog（欧普照明）
```

## 实战案例一：kingsun 勤上光电

### 发现过程

```
首页发现：
- "方案" 入口 → 隧道照明方案(180篇) + 道路照明方案(515篇) = 695篇合集
- 每个方案有独立详情页 URL（方案.html#id）
- "案例" 入口 → 4个子分类（outdoor 12 + landscape 12 + large_space 8 + interior 12）= 44篇

采集方式：
- 方案页：collector.py run kingsun（2篇合集，~14K字，111张图 ✓）
- 案例页：collector.py run kingsun_case（44篇独立详情，~295K字，~2,000张图 ✓）
```

**关键经验**：厂商官网的"方案"和"案例"通常是两个独立入口，均需单独评估和采集。

## 实战案例二：ltech 雷特

### 关键发现：隐藏在集合页背后的独立详情页

```
初始理解：Project-Cases/ 下 10 个集合页（每个含多个案例摘要）
爬取后分析：HTML 中发现了 73 个独立详情页链接！
每个详情页有完整的案例描述、参数、图片

成果：73 篇独立案例，~1,016K字，1,453 张图
注意：图片为外链防盗链，标注 manual
```

**关键经验**：集合页（listing/collection page）中可能包含隐藏的独立详情页链接。不要只看列表页面数量，要检查 HTML 中是否有可扩展的详情链接。

## 实战案例三：fsl 佛山照明

### 翻页模式

```
URL 模式：solution/{1-50} + application/{1-50}
爬取策略：使用脚本批量生成 URL 并探测存在性

实际采集：
- 方案页 27 篇（URL 编号约一半有效，非连续）
- 案例页 7 篇
- 2 个 LED 车灯 URL 超时 → 跳过
- 共 34 篇，~85K字，845 张图（manual）
```

**关键经验**：编号型 URL 通常不是全部连续有效，且单个页面的文字量差异大。

### 场景映射

```
工业 → factory
办公 → office
商超 → commercial
酒店 → hotel
景观 → landscape
户外 → outdoor
```

## 实战案例四：降级决策

### 欧普照明（opple）

```
评估结果：JS 动态加载，无独立详情页 URL
每个产品类目是一个 SPA 列表页
点击后 URL 不变，内容通过 AJAX 加载

决策：降级为 catalog 采集
→ 只保存页面资源/CSS/产品列表
→ 不做深度详情解析
```

### 雷士照明（nvc）

```
评估结果：品牌介绍 + 产品目录
无案例详情页，无可采集的方案文档

决策：降级为 catalog
→ 只做品牌概览采集（branding + product line）
→ 不纳入方案素材
```

### 涂鸦智能（tuya）

```
评估结果：IoT 平台介绍，无照明方案详情页
内容偏向技术平台（IoT SDK、网关、云平台）

决策：保持现状
→ 不作为照明方案素材
→ 可作为 IoT 技术参考保留
```

## 大规模批量采集的效率策略

### 交互式脚本 vs CLI 运行

```
方案 A：collector.py CLI 逐个运行
  → 问题：stdout 在后台进程中被缓冲，看不到实时进度
  → 解法：python -u collector.py run xxx（-u 运行）

方案 B：交互式 Python 脚本（直接调用内部函数）
  → 优势：实时 print 输出、动态调整参数、采集完成后自动触发清洗
```

### 实际数据

| 厂商 | 采集方式 | 篇数 | 文字量 | 图片 | 耗时 |
|------|---------|------|--------|------|------|
| kingsun | CLI run kingsun + kingsun_case | 2+44 | ~309K | ~2,111 | 较快 |
| ltech | CLI run ltech_all | 73 | ~1,016K | 1,453 | 中等 |
| fsl | 脚本批量 URL 探测 | 34 | ~85K | 845 | 较快 |

- Q: 厂商采集评估的四个维度是什么？
  A: ① 页面结构 — 静态/动态/SPA；② 详情页可发现性 — 独立URL/分组/仅目录；③ 反爬强度 — robots/频率/验证码；④ 内容质量 — 方案详情/产品参数/品牌介绍。

- Q: 发现隐藏在集合页（collection page）背后的独立详情页有什么技巧？
  A: 不要只看列表上的集合页数量。爬取集合页 HTML 后，检查其中是否有指向独立详情页的 URL link（通常每段案例摘要会链向完整页面）。ltech 就是通过此方法从 10 个集合页扩展到 73 个独立详情页。

- Q: 动态 JS 网站评估不通过时的降级策略是什么？
  A: 尝试 playwright → 失败则降级为 catalog：只保存页面的 HTML/CSS 资源快照，不做深度详情解析。典型例子：欧普照明（JS SPA 无独立 URL）、雷士照明（无案例详情页）。

- Q: 大规模批量采集时如何处理 stdout 缓冲问题？
  A: 使用 `python -u` 运行脚本（-u 强制 stdout/stderr 无缓冲），或用交互式 Python 脚本模式（直接调用内部函数）替代 CLI 运行，实现实时进度输出和动态参数调整。

- Q: 三大厂商采集实战的数据对比？
  A: kingsun — 2+44=46篇，~309K字，~2,111图（全下载 ✓）；ltech — 73篇，~1,016K字，1,453图（manual）；fsl — 34篇，~85K字，845图（manual）。
